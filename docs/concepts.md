# Concepts

portalc has one idea behind it: **an integration with a portal should be a dependency you can review, version and test, not a script that happens to work today.** Everything below follows from that.

## Compile time and run time are different programs

| | Compile time | Run time |
|---|---|---|
| Commands | `explore`, `repair` | `run`, `verify`, `build` |
| How often | When you add a flow, or when a portal changes | Every call, and nightly in CI |
| May use an LLM | Yes, eventually — it is a compiler | **Never** |
| Output | Schema, flow, fixture, evidence, a diff | Typed rows, or a named error |

An agent that reasons about a page is useful exactly once: when working out what the page *is*. Letting it decide, on every call, whether today's page still means what yesterday's meant is how you get an integration nobody can debug and nobody can price. So portalc spends model tokens at compile time, writes down what it learned, and runs the written-down version deterministically.

In v0.1 even the compile step uses no model: the HTTP engine handles a form login plus an HTML table, which is what most partner portals are.

## The artifacts

A compiled portal is a directory of text files. Every one of them exists to answer a question a reviewer will ask.

```
portals/demo-marina/
  portal.yaml                        what this portal is, and which env vars hold its secrets
  flows/list-invoices.flow.json      the steps, the params, and the header contract
  flows/list-invoices.checks.json    assertions that are not schema, e.g. minRows
  schemas/invoice.schema.json        JSON Schema 2020-12 for a row, plus x-portalc metadata
  fixtures/2026-09-20.list-invoices.json   what the portal actually returned, that day
  evidence/2026-09-20.list-invoices.html   the table region it came from
  CHANGELOG.md                       what changed about this portal, in words
generated/ts/portal-demo-marina/     the typed client, regenerated by portalc build
portalc.lock                         version, artifact hashes, last green run per flow
```

**`portal.yaml`** is the only file you write by hand. See [adding-a-portal.md](adding-a-portal.md).

**The flow** records what to do and, importantly, `headerContract`: the exact column titles the portal showed when the schema was agreed. That list is what turns a silent rename into a failing test.

**The schema** is ordinary JSON Schema, so anything can validate against it. portalc's own metadata lives under `x-portalc` — the header for each field, the table marker and the selector — which is namespaced so the rest of your toolchain can ignore it.

**The fixture and the evidence file** are the receipts. When a partner insists nothing changed on their side, the fixture is what the portal returned and the evidence is the markup it came from. They are also why you should read both before the first commit against a real portal: that is your data. See [SECURITY.md](../SECURITY.md#before-you-commit-compiled-artifacts).

**`portalc.lock`** carries a version per portal, a SHA-256 of the flow and the schema, and `lastGreenAt`. It is how `verify` knows which artifacts it is testing and how `repair` knows what to bump.

## Drift is the product

Portals do not break with a 500. They rename a column, reorder two, change a date format, or split one field into two, and keep returning HTTP 200. Nothing in your stack notices until a customer does.

portalc calls that drift and refuses to treat it as success:

- **`verify`** compares live headers against `headerContract`, validates every row against the schema, and applies the `checks.json` assertions. Its verdict is mechanical, which is what makes it safe to run unattended at 03:00.
- **`run`** applies the same schema validation and, on a mismatch, exits 6 with a drift error instead of returning rows that are the wrong shape. The generated TypeScript client turns exit 6 into a thrown `PortalDriftError`. Half-right data never reaches your database.
- **`repair`** re-reads the page and, if the only difference is a column's *title*, writes a patch: it confirms the reading twice, updates the header in the schema, bumps the portal's version, and leaves a pull request body behind. Field names — the identifiers your code uses — stay put, so a rename costs you a review, not a refactor.

Anything more interesting than a rename, `repair` leaves for a human on purpose. Guessing that a new column is "probably the old one" is how you silently reconcile against the wrong number.

## Versioning

Each portal has its own version in `portalc.lock`, and the generated client package carries it. A rename patch is a patch release, because your code does not change. A field that appears, disappears or changes type is a breaking change to the schema, and should be treated like any other breaking dependency bump: read the diff, then decide.

This is the practical difference from a hosted "portal API". When the vendor's endpoint changes shape, you find out from an incident. When a portalc schema changes shape, you find out from a pull request with a diff, a fixture and a changelog entry — and you choose when to take it.

## Engines

An engine is the thing that actually talks to the portal.

- **`http`** — the default. A cookie jar, a form POST to log in, a GET, and a table parsed out of the HTML. No browser, no model, milliseconds per call, and trivially testable.
- **`chrome`** — a real Chrome over CDP, for portals that render their table in JavaScript or that only let a human through the login. `run` and `verify` stay deterministic in it: navigate, wait for the document, extract by rule.
- **`browser-use`** — the optional agent, reachable only from `explore --agent` and `repair --agent`.

The split does not move with the engine: a browser may be used to *learn* a portal, and `verify` still does not ask a model whether the test passed. A flow compiled in Chrome is validated by the HTTP engine and the other way round, and both engines enforce the portal's `policy:` block on every request.

## What portalc is not

- **Not a scraper.** It needs your own account on a portal you are allowed to use, and it reads one flow you compiled on purpose.
- **Not a hosted API.** There is no portalc cloud. The artifact is in your repository and runs on your machine.
- **Not a replacement for a real API.** If the partner has one, use it. portalc is for the long tail that never will.
- **Not for banks.** Payment and account data has PSD2 and licensed providers. Do not point this at them.
